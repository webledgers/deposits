This extension standardises deterministic Bitcoin deposit addresses for any Web Ledgers instance whose owner is identified by a Nostr public key. A single compressed public key (depositKey) is published at the ledger root; every URI in the ledger deterministically maps—via a Taproot key‑tweak—to a unique Bitcoin address that only the owner can spend.

Scope and Purpose

The goal is to enable stateless deposit address generation—anyone who can read the ledger JSON can pay an entry without prior coordination or server API calls, while privacy is preserved by a fresh Taproot output per URI.

Terminology

Owner Key (P)
The 33‑byte compressed secp256k1 public key published in depositKey.
Target Identifier (I)
A URI contained in an Entry’s url field.
Tagged Hash
SHA‑256 construction H(tag, m) = SHA256(SHA256(tag)‖SHA256(tag)‖m) as used by BIP‑340.

Data‑Model Additions

A ledger supporting deterministic deposits MUST contain:

{
  "depositProtocol": "nostr-det-v1-taproot",
  "depositKey": "02c1...9f"
}

Address‑Derivation Algorithm

  1. Canonicalise I: lower‑case scheme/host, strip default ports and trailing slashes, punycode host.
  2. Compute tweak t: t := H("webledgers-deposit", I) mod n. If t = 0, append a null byte to I and retry.
  3. Add t to P: Q := P + t·G.
  4. Encode Q: use BIP‑350 Bech32m as a P2TR (witness v1) address.

The resulting address A(I) is the sole valid deposit address for I.

Security Considerations

  • Key exposure: leaking the private key compromises all deposits; operators SHOULD use HSMs.
  • Privacy: on‑chain linkability is minimised; however the public ledger itself reveals the mapping I → A(I).

Example

{
  "@context": "https://w3id.org/webledgers",
  "type": "WebLedger",
  "depositProtocol": "nostr-det-v1-taproot",
  "depositKey": "030f...9f",
  "entries": [
    { "type": "Entry", "url": "did:nostr:d17e...", "amount": "210000" }
  ]
}
